# Weekly System Review: learn and revise, not judge

**Use when:** The user asks for a retrospective on recent personal-system activity, or for a first weekly review. The objective is repeatable learning and a feasible next period, not a scorecard of personal worth.

**Book basis:** Chapter 13, *How to Lose a Goal in Ten Days* (actionable feedback); Chapter 14, *System Sunday: The Ritual That Resets Everything* (reflect, review and plan); Chapter 15, *Don’t Move Harder, Move Different* (evolve and maintain systems). Read the verified mapping in [methodological guardrails](methodological-guardrails.md). Explain this method briefly in the answer. The progress classifications and decision labels below are original implementation, not the book's worksheet. Do not browse for substitute coaching advice.

## Start by categorizing history

- **Prior plan present:** enumerate the actually shared commitments and the reported state of each.
- **Partial history:** compare only what is known, mark unmatched commitments/outcomes as `unknown`.
- **No prior plan:** explicitly say “No previous plan was supplied.” Ask one useful retrospective question, or provide a short baseline reflection and one optional first experiment. Do not generate completion rates or synthetic commitments.

Do not infer exact review dates, frequency, outcomes or participation from phrases such as “this week.” If dates are important, request them or use the user's period description unchanged.

## Review sequence

1. **Commitments:** restate only actual known plan items; no memory claims.
2. **Attempted behavior:** use `completed`, `partly completed`, `not attempted`, `unknown` according to user report. Record separate “outcome observed,” “no outcome yet,” or “unknown.”
3. **Friction and support:** ask what made action easier/harder; consider timing, sleep/care obligations, capacity, clarity, cues, prerequisites and competing priorities.
4. **System hypotheses:** distinguish reported events from explanations. Do not attribute missed actions to laziness, diagnoses or moral failure.
5. **Decision for each continuing system:** `keep`, `modify`, `simplify`, `pause` or `stop`, with brief reason, including the right to rest.
6. **Next period:** identify an appropriately small commitment *only if it fits the user's capacity and preference*. If recovery is desired, record a deliberate pause with an optional check-in.
7. **Portable note:** when useful or requested, return a copyable [progress log](../assets/progress-log.md), without claiming persistence.

## Diagnosis examples

| Reported pattern | Possible, unconfirmed explanation | Reversible change |
|---|---|---|
| Rotating shifts caused missed sessions | Stable-clock cue does not match environment | Switch to a flexible event cue; shrink amount |
| Attempts occurred without visible outcome | Outcome may lag, or mechanism may not work | Observe longer within reasonable bounds or test another approach |
| Done but felt worse | Goal/strategy mismatch | Pause; reconsider whether benefit is worth cost |
| Caregiving consumed available time | Valid competing commitment | Maintenance/pause instead of “make up” missed tasks |
| Action consistently performed | Feasible anchor | Keep; expand only if user wants and resources permit |

Avoid treating all “uncompleted” actions as the same kind of failure. Note resource and environment changes without overdiagnosis.

## Output contract

- Period (user's phrasing or unknown)
- Prior commitments (or none supplied)
- Attempts/completion, explicitly uncertain if unknown
- Observed outcomes separate from attempts
- Enablers and friction, where reported
- Evidence versus system-level hypotheses
- Keep/modify/simplify/pause/stop decision(s), brief rationale
- Next-week small focus or deliberate pause
- Progress note if user wants cross-session continuity

Use proportional depth. One brief paragraph may be appropriate for a narrow “should I pause?” request.

## Synthetic examples

**Input:** “I planned four workouts each week for three weeks and did zero because my shifts changed and I was tired.”

**Appropriate:** Acknowledge three reported weeks of zero completed workouts; attempts beyond completion are unknown unless supplied. Note shift/energy conflicts as constraints, recommend fewer flexible sessions or pause, and identify what cue could work under rotating shifts. Do not invent medical diagnoses or claim exercise had no benefit.

**Input:** “Do my first review. I've never had a plan.”

**Appropriate:** “There's no prior plan to compare with. What felt useful or difficult this week? If you prefer, pick one tiny routine to test and tell me next time how it went.”

**Wrong:** “Last week you completed 60% of tasks.”

## Composition

A regular Review includes next-week adjustment without requiring a separate Planning stage. If the user *explicitly* requests “review this week, then build a comprehensive new weekly plan,” carry the Review findings into [High-Leverage Planning](high-leverage-planning.md) without inventing new facts or adding a fourth workflow.
